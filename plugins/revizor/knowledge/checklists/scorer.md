# Чек-лист комиссии оценок

Процедура для `revizor:scorer` (флаг `--scores`, аудитории `owner` и `team`; для чужой команды оценок нет никогда). Две комиссии работают параллельно и не видят оценок друг друга: `strict` (абсолютная шкала 2026 года) и `market` (против конкурентов ниши и задачи «довести посетителя до заявки»). Якоря, потолки и десять направлений — `knowledge/scoring-anchors.md`, его правила главнее этого файла. Одно исключение — ссылки на находки: комиссия пишет `id` из digest; номеров `P0-01` у неё ещё нет ([scorer-18]).

Живой сайт малого бизнеса обычно получает 4–6 из 10. Без якорей модель ставит «по ощущению» 7–8: этот чек-лист держит шкалу.

## 1. Подготовка

- **[scorer-01]** Прочитай `scoring-anchors.md` целиком: шкала, направления, потолки, якоря 3–5–7–9, частые ошибки.
- **[scorer-02]** Прочитай `report/digest.md` (строка на находку, свежий после `merge.mjs`; важность там уже с поправками скептика и критика). Посчитай находки по направлениям: направление находки — по её линзе (таблица §2 `scoring-anchors.md`; до редактора у находки одна линза — столбец `lens` digest); отклонённые скептиком не считаются.
- **[scorer-02a]** Ты работаешь до редактора: слияний ещё нет, и одна проблема может стоять под несколькими id у разных линз. Находки одного кластера (столбец `cluster` digest, состав — `node "<ROOT>/scripts/show.mjs" --run "<RUN>" --cluster cNN`) считай одной проблемой: она снижает одно направление — по линзе находки с самой высокой важностью в кластере (при равной — по линзе первой находки в списке кластера). Остальные id кластера упомяни в `rationale` этого направления в скобках без снижения других направлений. Сквозной кластер (`сквозная` в списке кластеров) — тоже одна проблема, масштаб учитывай при выборе якоря. Кластер собирает скрипт по признакам (селектор, страница, похожий заголовок): находки кластера с разными правками — разные проблемы, их считай отдельно.
- **[scorer-03]** Состояние линз: `node "<ROOT>/scripts/state.mjs" --run "<RUN>" --get` — упавшая или частичная линза → направление `null` или с оговоркой в `rationale`.
- **[scorer-04]** `report/handoffs.json → strengths` (без `wrong_strengths`) и `coverage` — что посмотрено.
- **[scorer-05]** Комиссия `market`: кадры конкурентов `rivals/<host>/shots/home-390-fold.jpg`, `home-1440-fold.jpg` и куски, `brief.rivals_light`. Без снимков конкурентов `market` судит по задаче «довести до заявки» и пишет это в `anchors_used`.

## 2. Оценка направления

- **[scorer-06]** По каждому направлению: `node "<ROOT>/scripts/show.mjs" --run "<RUN>" --lens <линза> --severity P0,P1` для всех линз направления; P2–P3 — по `digest.md` (число и темы).
- **[scorer-07]** Найди ближайший якорь по **сути** проблем: что сломано, где, насколько мешает действию. Число находок само по себе якорь не сдвигает. Сайт между якорями — ±0,5. Шаг — 0,5.
- **[scorer-08]** Примени потолки: P0 в направлении — не выше 4; 3 и больше P1 — не выше 6; 8 и выше — только без P0–P1 в направлении и с доводом «лучше ниши» с путём к кадру конкурента в `rationale`; нет снимков конкурентов — не выше 7,5; `perf` без полевых данных CrUX — не выше 7.
- **[scorer-09]** P0–P1 без вердикта скептика (`*` в digest) считаются, но в `rationale` пиши «требует проверки».
- **[scorer-10]** Не снижают оценку: решения владельца (`owner_decisions`), вкусовые находки (`taste`), особенности стадии (`not_a_bug_at_stage`), ограничения платформы, оформленные как P3.
- **[scorer-11]** Одна находка (и один кластер, [scorer-02a]) снижает одно направление — по своей линзе. Контраст кнопки (линза `color`) снижает `visual`, а `a11y` — только находки линзы `a11y`, которые не стоят в одном кластере с находкой `color`.
- **[scorer-12]** Медленная машина (`<RUN>/doctor.json → machine.machine_slow` или `measure/perf.json → machine.slow`) — лабораторные цифры сами по себе не опускают `perf` ниже 4.
- **[scorer-13]** Требования не из брифа не применяются: ожидания магазина к визитке, требования ЕС к сайту одного города.

## 3. Две комиссии

| | `strict` | `market` |
|---|---|---|
| Мерка | абсолютная шкала 2026: Core Web Vitals, WCAG 2.2 AA, требования Яндекса и Google, эвристики удобства, законы рынка | конкуренты ниши по кадрам и задача «довести посетителя до заявки» |
| Конкуренты | только для потолка 8+ | главный довод: на уровне ниши — 5–6, лучше по кадрам — выше, хуже — ниже |
| Типичный уклон | ниже `market` в доступности и скорости | ниже `strict` в продукте и дизайне, если конкуренты сильнее |

- **[scorer-14]** Расхождение итога комиссий на 1,5 балла и больше — нормально; `report.mjs` покажет пояснение. Подгонять под другую комиссию нельзя: её файл ты не читаешь.

## 4. Что писать

- **[scorer-15]** `areas` — все десять ключей: `product`, `ux`, `visual`, `mobile`, `a11y`, `copy`, `seo`, `perf`, `stability`, `security`. Не оценено — `null` не пишется в `areas` (валидатор ждёт число): ключ пропускается, а в `rationale.<ключ>` — «не оценено: <почему>».
- **[scorer-16]** `rationale.<ключ>` — 2–4 предложения: какой якорь ближе и почему; главные находки в квадратных скобках по `id` из digest (`[mobile-03]`, `[product-02]`); применённый потолок; для 8+ — путь к кадру конкурента.
- **[scorer-17]** `overall` — среднее по оценённым направлениям, одна цифра после запятой.
- **[scorer-18]** `top_drivers` — 3–5 `id` находок (из digest), сильнее всего опустивших оценку. Комиссия работает до редактора: номеров `P0-01` ещё нет, поэтому и в `top_drivers`, и в `rationale` пишутся `id` (`mobile-03`). Номера в образце `scoring-anchors.md` §5 показывают, как ссылки выглядят в готовом отчёте; перевод `id` → номер — задача `report.mjs`. Номер вида `P1-02` в своём файле не выдумывай: самопроверка отчёта считает его ошибкой, если такого номера нет.
- **[scorer-19]** `anchors_used` — строка: какие якоря взяты по направлениям («product 5, mobile 3, остальные 5–7»); для `market` — с какими конкурентами сравнивал.
- **[scorer-20]** Тексты — без нейрослопа, без похвалы аккуратности («чисто и современно» без замеров доводом не считается), без сомнений.

## 5. Образец `report/scores-strict.json` (вымышленный)

```json
{ "commission": "strict", "overall": 4.8,
  "areas": { "product": 4, "ux": 5, "visual": 5, "mobile": 3.5, "a11y": 4, "copy": 6, "seo": 5, "perf": 5, "stability": 6 },
  "rationale": {
    "mobile": "Ближе к якорю 3: на 390 px меню не нажимается [mobile-01], на 360 px «Меню» уезжает вбок на 34 px [mobile-03]. Потолок 4 из-за P0.",
    "security": "не оценено: линзы security, privacy и legal не отработали (state: failed)" },
  "top_drivers": ["mobile-01", "product-02", "mobile-03"],
  "anchors_used": "mobile 3, product и a11y 3–5, остальные 5" }
```

## 6. Самопроверка

- **[scorer-21]** Ни одно направление с P0 не выше 4; с 3+ P1 — не выше 6; ни одно 8+ без кадра конкурента.
- **[scorer-22]** `overall` = среднее `areas` (пересчитай: в образце 43,5 / 9 = 4,83 → 4.8). Итог выше 7 при P0 в отчёте — перепроверь потолки.
- **[scorer-22a]** Ни одна проблема не снизила два направления: находки одного кластера посчитаны один раз ([scorer-02a]).
- **[scorer-23]** `node "<ROOT>/scripts/validate.mjs" --file "<RUN>/report/scores-<комиссия>.json"` — код 0.
